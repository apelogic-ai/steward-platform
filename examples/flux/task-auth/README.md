# task-auth install with Flux

The [task-auth profile](../../../docs/profiles/task-auth.md) in its production
shape, as Flux objects: the same releases, order and values as the
[helmfile reference install](../../../helmfile/README.md) for the same
environment. Everything here except this README is generated by
[`scripts/generate.sh`](../../../scripts/generate.sh) from
[`environments/production-task-auth/platform-values.yaml`](../../../environments/production-task-auth/platform-values.yaml)
and [`bom/bom.json`](../../../bom/bom.json); CI fails if the committed files
differ from a fresh generation.

| File | Objects | helmfile counterpart |
|---|---|---|
| [`cert-manager.yaml`](cert-manager.yaml) | `OCIRepository` for the BOM cert-manager chart, pinned by digest; `HelmRelease` | `cert-manager` |
| [`steward.yaml`](steward.yaml) | `OCIRepository` for the BOM Steward chart, pinned by digest; `HelmRelease` with `taskIdentity`, after cert-manager | `steward` |
| [`gateway-api-crds.yaml`](gateway-api-crds.yaml) | `GitRepository` of Gateway API at the v1.6.1 commit; `Kustomization` that server-side applies `config/crd/standard` | the `envoy-gateway` presync hook, first manifest |
| [`envoy-gateway-crds.yaml`](envoy-gateway-crds.yaml) | `OCIRepository` for the BOM Envoy Gateway chart at its digest, extracted; `Kustomization` that server-side applies its CRD directory, after the Gateway API CRDs | the `envoy-gateway` presync hook, second manifest |
| [`envoy-gateway.yaml`](envoy-gateway.yaml) | `OCIRepository` for the BOM Envoy Gateway chart, pinned by digest; `HelmRelease` without CRDs | `envoy-gateway` |
| [`steward-edge.yaml`](steward-edge.yaml) | `GitRepository` of this repository at the platform version's tag; `HelmRelease` of [`charts/steward-edge`](../../../charts/steward-edge): Steward's task API `HTTPRoute` and `BackendTLSPolicy`, after steward and envoy-gateway | `steward-edge` |
| [`github-oidc-exchange.yaml`](github-oidc-exchange.yaml) | `OCIRepository` for the BOM github-oidc-exchange chart, pinned by digest; `HelmRelease`, after envoy-gateway | `github-oidc-exchange` |
| [`kustomization.yaml`](kustomization.yaml) | Lists them all, for a Flux `Kustomization` or `kubectl apply -k` | |

The objects go in `flux-system`; each `HelmRelease` installs into its own
namespace. CI validates them against the CRD schemas of the Flux release
pinned in [`scripts/ci/install-tools.sh`](../../../scripts/ci/install-tools.sh)
(2.9.5), and reconciles part of them with its controllers. The `HelmRelease`s
use `install.strategy` and `upgrade.strategy`, which older Flux releases do
not have.

## What the operator supplies

This output targets the production shape. It contains no evaluation piece:
no self-signed CA, no in-cluster PostgreSQL, no evaluation Gateway. Those are
in-repo charts that only the helmfile installs, and an environment that uses
any of them gets no Flux output. Before Flux reconciles, create:

- everything the [core production shape](../../../helmfile/README.md#production-shape)
  needs: the PostgreSQL database, its Secret (`database.secret`) and CA
  (`database.tls.ca`), and the cert-manager issuer (`tls.certManager.issuer.ref`);
- **the Gateway** named in `edge.gateway` (`edge.gateway.source: operator`),
  with an HTTPS listener (`edge.gateway.listener`) that serves both public
  hostnames and admits routes from the Steward and exchange namespaces. Its
  `GatewayClass` can use the Envoy Gateway controller installed here;
- **the Steward API CA** ConfigMap named in `edge.stewardBackendCaConfigMap`,
  in the Steward namespace, which the `BackendTLSPolicy` trusts; publish it
  with your trust distribution (for example trust-manager);
- the exchange's **policy ConfigMap and keyring Secret** in
  `namespaces.identityExchange`, and its **public JWKS ConfigMap**
  (`identityExchange.publicJwksConfigMap`) in the Steward namespace. See the
  exchange's [integration guide](https://github.com/apelogic-ai/github-oidc-exchange/blob/v0.7.2/docs/integration.md).

Secrets are referenced by name, never generated.

## Use it

```sh
cp -r environments/production-task-auth environments/<name>   # then edit it
scripts/generate.sh environments/<name>/platform-values.yaml
# copy generated/<name>/flux/ into the Git path your Flux Kustomization watches
```

Generate from a released platform version: `steward-edge.yaml` fetches
[`charts/steward-edge`](../../../charts/steward-edge) from this repository at
the tag of the BOM's `platformVersion`, which exists once that version is
released. With `edge.install: false` (the cluster already runs a Gateway API
implementation with `BackendTLSPolicy`), the output has no CRD objects and no
Envoy Gateway release.

## How the helmfile's hooks map to Flux

- **CRD manifests.** The helmfile's `envoy-gateway` presync hook downloads the
  BOM's Gateway API and Envoy Gateway CRD manifests, checks their SHA-256 and
  server-side applies them ([`scripts/apply-manifests.sh`](../../../scripts/apply-manifests.sh)).
  Flux cannot fetch an HTTPS file checked by SHA-256, so each manifest has a
  BOM `fluxSource` that Flux pins itself: Gateway API from its Git repository
  at the release commit, Envoy Gateway's from the BOM Envoy Gateway chart at
  its digest. A `Kustomization` server-side applies each, Gateway API first,
  with `prune: false` so that no CRD (and none of its objects) is ever deleted.
  [`tests/flux/run.sh`](../../../tests/flux/run.sh) proves on every run that
  each source, at its pin, holds exactly the objects of the SHA-256-pinned
  manifest. A BOM bump that changes the CRDs updates them on the next
  reconcile, as the helmfile's hook does.
- **Order.** Each `dependsOn` is the helmfile `needs` of the same release.
  Flux cannot order a `HelmRelease` after a `Kustomization`, so the releases
  that need the edge CRDs (envoy-gateway, steward-edge, github-oidc-exchange)
  use `install.strategy` and `upgrade.strategy` `RetryOnFailure`: they retry
  every minute until the CRDs exist, instead of remediating three times and
  stalling. Envoy Gateway's own chart CRDs are off, and its `HelmRelease`
  skips CRDs on install and upgrade: the Kustomizations own them.
- **Evaluation-only releases** (`evaluation-ca`, `postgresql-evaluation`,
  `edge-evaluation-ca`, `evaluation-edge`) are not emitted; the operator
  supplies their production equivalents, above.

## What CI checks

[`tests/flux/run.sh`](../../../tests/flux/run.sh), with no cluster:

- the files match a fresh generation, and validate strictly against the Flux
  CRD schemas (kubeconform);
- the `HelmRelease`s are exactly the helmfile's releases for the same
  environment, each `dependsOn` is exactly that release's `needs`, and each
  carries exactly the generated values the helmfile installs, in the same
  namespace;
- each `OCIRepository` pins its BOM chart by digest; each chart renders with
  the `HelmRelease` values and the BOM image digests;
- each CRD `Kustomization` matches the helmfile hook's manifests, in order,
  and its source holds exactly the manifest's objects;
- `charts/steward-edge` at the platform tag is the chart in this checkout.

[`tests/flux/reconcile.sh`](../../../tests/flux/reconcile.sh) installs Flux in
kind and reconciles the edge part of this example: both CRD Kustomizations,
envoy-gateway and steward-edge (without its dependency on the steward
release). It checks every CRD object on the cluster and the resulting
routes. Steward, cert-manager and the exchange are not reconciled there,
since they need the operator inputs above; their values are the helmfile's,
which the [task-auth end-to-end test](../../../tests/e2e/task-auth/README.md)
proves on a live cluster.

## Upgrades and the Steward CRD

Steward's `AgentRuntime` CRD is in its chart's `crds/` directory. The Steward
`HelmRelease` creates it on install and skips it on upgrade
(`install.crds: Create`, `upgrade.crds: Skip`), Helm's own behaviour. When a
BOM bump moves Steward to a new chart, read the Steward release's upgrade
notes, then apply the new CRD before Flux reconciles the new chart:

```sh
helm show crds "$(jq -r '.products.steward.chart | "\(.reference)@\(.digest)"' bom/bom.json)" \
  | kubectl --context <context> apply --server-side -f -
```

See [helmfile/README.md](../../../helmfile/README.md#upgrades-and-the-steward-crd).
The Gateway API and Envoy Gateway CRDs upgrade with their `Kustomization`s;
cert-manager's are chart templates and upgrade with its release.
