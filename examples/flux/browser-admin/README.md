# browser-admin install with Flux

The [browser-admin profile](../../../docs/profiles/browser-admin.md) in its
production shape, as Flux objects: the same releases, order and values as the
[helmfile reference install](../../../helmfile/README.md) for the same
environment. Everything here except this README is generated by
[`scripts/generate.sh`](../../../scripts/generate.sh) from
[`environments/production-browser-admin/platform-values.yaml`](../../../environments/production-browser-admin/platform-values.yaml)
and [`bom/bom.json`](../../../bom/bom.json); CI fails if the committed files
differ from a fresh generation.

It is the [task-auth Flux example](../task-auth/README.md) with two
differences, both from the helmfile:

- **Steward renders its own edge** (`web.httpRoute`): the `steward-api` and
  `steward-web` `HTTPRoute`s and the `BackendTLSPolicy`, next to its web UI and
  Google Workspace browser login. There is no `steward-edge.yaml`, and so no
  `GitRepository` of this repository.
- **Steward follows envoy-gateway** (`dependsOn`), as in the helmfile, and,
  like every release that creates Gateway API objects, retries until the
  edge CRDs exist (`RetryOnFailure`).

| File | Objects | helmfile counterpart |
|---|---|---|
| [`cert-manager.yaml`](cert-manager.yaml) | `OCIRepository` for the BOM cert-manager chart, pinned by digest; `HelmRelease` | `cert-manager` |
| [`steward.yaml`](steward.yaml) | `OCIRepository` for the BOM Steward chart, pinned by digest; `HelmRelease` with task identity, browser login, the web UI and Steward's own routes, after cert-manager and envoy-gateway | `steward` |
| [`gateway-api-crds.yaml`](gateway-api-crds.yaml) | `GitRepository` of Gateway API at the v1.6.1 commit; `Kustomization` that server-side applies `config/crd/standard` | the `envoy-gateway` presync hook, first manifest |
| [`envoy-gateway-crds.yaml`](envoy-gateway-crds.yaml) | `OCIRepository` for the BOM Envoy Gateway chart at its digest, extracted; `Kustomization` that server-side applies its CRD directory, after the Gateway API CRDs | the `envoy-gateway` presync hook, second manifest |
| [`envoy-gateway.yaml`](envoy-gateway.yaml) | `OCIRepository` for the BOM Envoy Gateway chart, pinned by digest; `HelmRelease` without CRDs | `envoy-gateway` |
| [`github-oidc-exchange.yaml`](github-oidc-exchange.yaml) | `OCIRepository` for the BOM github-oidc-exchange chart, pinned by digest; `HelmRelease`, after envoy-gateway | `github-oidc-exchange` |
| [`kustomization.yaml`](kustomization.yaml) | Lists them all, for a Flux `Kustomization` or `kubectl apply -k` | |

## What the operator supplies

Everything the [task-auth Flux example](../task-auth/README.md#what-the-operator-supplies)
needs (the database, its Secret and CA, the issuer, the Gateway, the Steward
API CA ConfigMap, and the exchange's policy, keyring and public JWKS), and:

- the **Google OAuth client Secret** named in `browserAuth.google.clientSecret`,
  in the Steward namespace, holding only the raw client secret;
- **literal CIDRs for Google's sign-in endpoints** in
  `networkPolicy.egressCidrs.browserAuth`, which you maintain; production
  refuses `0.0.0.0/0` ([apelogic-ai/steward#152](https://github.com/apelogic-ai/steward/issues/152)).

Then follow the [first-admin runbook](../../../docs/browser-admin/first-admin.md).

## Use it, CI checks, upgrades

As for [task-auth](../task-auth/README.md#use-it): copy
`environments/production-browser-admin`, edit it, generate, and copy
`generated/<name>/flux/` into the Git path your Flux `Kustomization`
watches. The [hooks mapping](../task-auth/README.md#how-the-helmfiles-hooks-map-to-flux),
the [static checks](../task-auth/README.md#what-ci-checks) (including the
BOM web image in the rendered Steward chart) and the
[Steward CRD upgrade steps](../task-auth/README.md#upgrades-and-the-steward-crd)
are the same. CI does not reconcile this example with Flux controllers: the
edge part is the task-auth one, which it does reconcile, and Steward needs the
operator inputs; the [browser-admin end-to-end test](../../../tests/e2e/browser-admin/README.md)
proves the same values on a live cluster through the helmfile.
