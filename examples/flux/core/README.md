# Core install with Flux

The same core install as the [helmfile reference install](../../../helmfile/README.md),
expressed as Flux objects. Everything here except this README is generated by
[`scripts/generate.sh`](../../../scripts/generate.sh) from
[`environments/production/platform-values.yaml`](../../../environments/production/platform-values.yaml)
and [`bom/bom.json`](../../../bom/bom.json); CI fails if the committed files
differ from a fresh generation, so they cannot drift from the BOM.

| File | Objects |
|---|---|
| [`cert-manager.yaml`](cert-manager.yaml) | `OCIRepository` for the BOM cert-manager chart, pinned by digest; `HelmRelease` with every image pinned by digest |
| [`steward.yaml`](steward.yaml) | `OCIRepository` for the BOM Steward chart, pinned by digest; `HelmRelease` that depends on cert-manager |
| [`kustomization.yaml`](kustomization.yaml) | Lists both, for a Flux `Kustomization` or `kubectl apply -k` |

The objects go in `flux-system`; each `HelmRelease` installs into its own
namespace (`targetNamespace`). They need Flux 2.6 or later
(`source.toolkit.fluxcd.io/v1` `OCIRepository`, `helm.toolkit.fluxcd.io/v2`
`HelmRelease`). CI validates them against the CRD schemas of the Flux release
pinned in [`scripts/ci/install-tools.sh`](../../../scripts/ci/install-tools.sh).

## Use it

This example is production-shaped: it has no evaluation database or
self-signed CA, and its addresses are documentation placeholders. Generate
your own from your platform values:

```sh
cp -r environments/production environments/<name>   # then edit it
scripts/generate.sh environments/<name>/platform-values.yaml
# copy generated/<name>/flux/ into the Git path your Flux Kustomization watches
```

Before Flux reconciles, create what the production shape expects from the
operator: the database, its Secret and CA, and the cert-manager issuer. The
list is in [helmfile/README.md](../../../helmfile/README.md#production-shape);
it is the same for Flux.

An environment that uses the evaluation pieces (such as `kind`) gets no Flux
output. Those are in-repo charts that only the helmfile installs.

The task-auth and browser-admin profiles have their own examples,
[`../task-auth`](../task-auth/README.md) and
[`../browser-admin`](../browser-admin/README.md), which add the edge CRDs,
Envoy Gateway, the Steward edge routes and github-oidc-exchange.

## What CI checks

[`tests/flux/run.sh`](../../../tests/flux/run.sh):

- the files match a fresh generation;
- every object validates, strictly, against the Flux CRD schemas (kubeconform);
- the `HelmRelease`s are the helmfile's releases for the same environment,
  each `dependsOn` is that release's helmfile `needs`, and each carries
  exactly the generated values the helmfile installs;
- each `OCIRepository` points at its BOM chart and pins only its BOM digest,
  and each `HelmRelease` takes its chart from that `OCIRepository`;
- each chart, pulled at that digest, renders with the `HelmRelease` values
  and uses the BOM image digests.

CI does not reconcile this example with Flux controllers (it needs the
operator's database and issuer). The values are the ones the helmfile
installs, and the [core end-to-end test](../../../tests/e2e/core/README.md)
proves those on a live cluster.

## Upgrades and the Steward CRD

Steward's `AgentRuntime` CRD is in its chart's `crds/` directory. The Steward
`HelmRelease` creates it on install and skips it on upgrade
(`upgrade.crds: Skip`), which is Helm's own behaviour: a CRD change is applied
deliberately, after reading the Steward release notes. See
[helmfile/README.md](../../../helmfile/README.md#upgrades-and-the-steward-crd).
cert-manager's CRDs are chart templates (`crds.enabled: true`) and upgrade with
its release.
