# Steward platform 2026.10.0-alpha.7

A pre-release of the Steward platform BOM that moves every product to its
current patch release: Steward 0.3.3, github-oidc-exchange 0.7.4,
steward-run 0.7.5 and, for the planned governed profile, mcp-gw 0.5.1. The
platform itself (generator, helmfile, Flux output, scripts, platform values
schema) is unchanged from
[2026.10.0-alpha.6](2026.10.0-alpha.6.md). It is an alpha: the governed
profile, which runs agents, is not in it yet.

**No breaking changes for the core, task-auth and browser-admin profiles.**
Platform values written for alpha.6 validate unchanged and generate the same
install with the new product coordinates. The steward-run 0.7.5 image fixes
CVE-2026-75803 (OpenSSL); see
[steward-run 0.7.5](#steward-run-075). Steward 0.3.3 tightens the
governed-mode preflight and requires provider-profile bundle 1.2.1: that
matters only if you run Steward's governed execution yourself, outside this
BOM ([Steward 0.3.3](#steward-033)). mcp-gw stays at 0.5.1, not 0.5.2
([why](#mcp-gw-051)).

[`bom/bom.json`](../../bom/bom.json) at this version is authoritative. The
tables below abbreviate digests to 12 hex characters for reading; install from
the full digests in the BOM, never from tags.

### What changed in each product

#### Steward 0.3.3

[Release notes](https://github.com/apelogic-ai/steward/releases/tag/v0.3.3),
[changelog](https://github.com/apelogic-ai/steward/blob/v0.3.3/CHANGELOG.md).

- A patch release with no database migration and no chart default change.
  The chart is identical to 0.3.2 apart from its version and a README section
  on OpenShell 0.0.98, so the generated Steward values are unchanged apart
  from the image tags and digests. Rolling back to 0.3.2 needs no database
  rollback.
- Governed execution only: the platform preflight now requires
  `execution.endpoints.mintAudience` to equal `config.mint.audience`, rejects
  unrestricted, loopback and link-local provider CIDRs, and checks the MCP-GW
  endpoint coupling; provider-profile bundle 1.2.1 is required. None of this
  applies to the profiles in this BOM, which run Steward with
  `execution.enabled: false`.

#### github-oidc-exchange 0.7.4

[0.7.4 release notes](https://github.com/apelogic-ai/github-oidc-exchange/blob/v0.7.4/docs/releases/v0.7.4.md),
[0.7.3 release notes](https://github.com/apelogic-ai/github-oidc-exchange/blob/v0.7.4/docs/releases/v0.7.3.md),
upgrade guides
[0.7.3](https://github.com/apelogic-ai/github-oidc-exchange/blob/v0.7.4/docs/upgrade-v0.7.3.md) and
[0.7.4](https://github.com/apelogic-ai/github-oidc-exchange/blob/v0.7.4/docs/upgrade-v0.7.4.md).
Routes, audiences, policy schemas, token lifetime and the default
`steward-task-v2` output are unchanged.

- **Egress fix.** The chart's default egress policy now allows the
  Kubernetes API server on TCP 443 and 6443, over IPv4 and IPv6, so the
  Lease replay ledger works where the API server is reached on port 6443
  after Service address translation
  ([apelogic-ai/github-oidc-exchange#58](https://github.com/apelogic-ai/github-oidc-exchange/issues/58),
  which kept Kubernetes 1.35 and 1.36 out of the alpha.5 window). HTTPS
  egress also gains `::/0`. 0.7.4 adds an ingress rule that admits DNS
  replies only from the configured DNS peers, for CNIs that do not keep DNS
  reply state.
- **New chart values, left at their defaults.** `networkPolicy.dnsIpBlocks`,
  `httpsEgressCidrs`, `apiServerCidrs`, `apiServerPorts`, `extraEgress` and
  `rolloutAutomation.reloader.enabled` (an opt-in for an operator-managed
  Stakater Reloader, off by default) are not set by the generator, so the
  chart defaults apply. The platform keeps setting `rolloutRevisions` from the
  platform values, as before.
- `keyring-tool` ships in the signed image
  ([apelogic-ai/github-oidc-exchange#55](https://github.com/apelogic-ai/github-oidc-exchange/issues/55)).
  JWKS fetch failures now log the failing stage and cause.
- The release is published directly to GHCR. The signer
  (`release.yml` on `main`), the release manifest and the signature asset
  names (`public-image-signature.sigstore.json`,
  `public-chart-signature.sigstore.json`) are unchanged.

#### steward-run 0.7.5

Release notes
[0.7.5](https://github.com/apelogic-ai/steward-run/blob/v0.7.5/docs/release-notes-v0.7.5.md),
[0.7.4](https://github.com/apelogic-ai/steward-run/blob/v0.7.5/docs/release-notes-v0.7.4.md) and
[0.7.3](https://github.com/apelogic-ai/steward-run/blob/v0.7.5/docs/release-notes-v0.7.3.md).

- **Security fix.** The runner image fixes CVE-2026-75803 (OpenSSL), and the
  container-based reusable workflow's job container is re-pinned to an image
  with the fix. steward-run's notes state that rolling back to 0.7.4
  reintroduces the vulnerability; the 0.7.2 that alpha.6 pins predates the
  fix.
- **Action inputs unchanged.** The action gains the outputs `outcome`,
  `failure-category` and `http-status`, and from 0.7.3 installs Node 24
  itself when `PATH` has none. The task-auth end-to-end test runs the action
  at the new commit with the same inputs.
- **Manifest coordinates.** The signed manifest is still schema 3. From
  0.7.5 it records the tag commit as both `workflowCommit` and
  `actionCommit`, so the BOM's action and workflow commits are both
  `302d854c995e`. Steward's `config.apiserver.stewardRunRelease`, which the
  generator projects from the BOM for browser-admin, changes accordingly:
  `version`, `workflowCommit`, `actionCommit` and
  `governedJobContainerImage`. `verify-signatures.sh` checks that the
  projection equals the signed manifest field for field.
- **Signer identity.** From 0.7.3 the release is signed by
  `portable-release.yml` at the exact release tag, so the BOM's
  `certificateIdentity` is now `...portable-release.yml@refs/tags/v0.7.5`
  instead of `@refs/heads/main`.
- 0.7.4 adds HTTP(S) proxy support and an egress inventory; 0.7.5 vendors the
  ARC subchart (offline packaging) and documents a
  [fork rebuild](https://github.com/apelogic-ai/steward-run/blob/v0.7.5/docs/customer-rebuild.md).

#### mcp-gw 0.5.1

[Changelog](https://github.com/apelogic-ai/mcp-gw/blob/v0.5.1/CHANGELOG.md).

- **Pinned at 0.5.1, not 0.5.2.** mcp-gw 0.5.2 has a regression: Google
  Workspace tool calls fail with the default `GWS_BINARY_PATH`
  ([apelogic-ai/mcp-gw#100](https://github.com/apelogic-ai/mcp-gw/issues/100)).
  A later BOM moves on once a fixed release exists.
- 0.5.1 adds configurable AgentGateway CORS allowlists and backend failure
  behavior, runs the wrappers with read-only root filesystems, and scopes the
  internal NetworkPolicy peers to the same Helm release. No database
  migration, Secret change or reauthorization is needed; see its upgrade
  notes.

## Upgrading from 2026.10.0-alpha.6

- **Platform values** from alpha.6 validate against the current schema
  unchanged and, with this BOM, generate exactly what alpha.6's generator
  generates; CI checks this for every committed environment of every
  platform release tag. Regenerating with this BOM
  changes only product coordinates: the product chart digests, the image tags
  and digests, Steward's `stewardRunRelease` (browser-admin), the
  `platformVersion` in the header comments and, in the task-auth Flux output,
  the `steward-platform` `GitRepository` tag, to `2026.10.0-alpha.7`.
  `charts/steward-edge` is unchanged.
- **Apply** with `helmfile --environment <env> --kube-context <context>
  sync`, or let Flux reconcile the regenerated objects. Steward adds no
  migration. github-oidc-exchange rolls its pods to the new image.
- **github-oidc-exchange egress widens.** With the chart defaults, the
  exchange's NetworkPolicy now allows egress to the API server on TCP 443 and
  6443 to any IPv4 or IPv6 address, where 0.7.2 allowed TCP 443 to any IPv4
  address, and admits DNS replies from the cluster DNS. The platform values
  have no field to narrow these yet; see [known issues](#known-issues).
- **steward-run callers.** Repositories that pin the steward-run action or
  reusable workflow by commit, including workflows Steward generated from the
  previous `stewardRunRelease`, keep running 0.7.2 until they are updated to
  commit `302d854c995e` **(inferred from the steward-run notes: the fix is in
  the image and the job container that 0.7.5 pins)**. Update them to get the
  CVE-2026-75803 fix.
- **Steward governed users** (outside this BOM): before the Helm upgrade to
  0.3.3, follow Steward's provider-profile bundle 1.2.0 to 1.2.1 transition
  from a checkout of the `v0.3.3` tag, re-apply both profiles under their
  existing IDs and rerun the platform preflight with
  `execution.endpoints.mintAudience` set. See the
  [bundle upgrade procedure](https://github.com/apelogic-ai/steward/blob/v0.3.3/config/provider-profile-bundle/v1.2.1/README.md)
  and the [Steward 0.3.3 changelog](https://github.com/apelogic-ai/steward/blob/v0.3.3/CHANGELOG.md).
- **mcp-gw** is not installed by any profile. If you install the pinned
  mcp-gw yourself, read its 0.5.1 upgrade notes: the wrappers' root
  filesystems become read-only, and the internal NetworkPolicies require the
  AgentGateway Pod's `app.kubernetes.io/instance` label to match the release.
- **Registry mirror.** Copy the new product artifacts before regenerating:
  `scripts/mirror-list.sh` lists them, and `scripts/verify-digests.sh --mirror
  <platform-values>` checks the copy.
- **Built from source.** Rebuild Steward and github-oidc-exchange at the new
  release commits and write a new lock: the lock's versions, chart versions
  and commits must equal this BOM's, so an alpha.6 lock is refused. The
  releases that document their fork builds (github-oidc-exchange 0.7.4) are
  now the ones the BOM pins
  ([#34](https://github.com/apelogic-ai/steward-platform/issues/34)).
- **Coming from a pre-platform install**: follow the
  [migration runbook](../upgrades/from-pre-platform.md) to the alpha.6
  product set, then this section.
- **Rolling back** to alpha.6 means generating from an alpha.6 checkout.
  Steward 0.3.3 to 0.3.2 needs no database rollback. github-oidc-exchange
  documents 0.7.3 as the rollback pair of 0.7.4 and 0.7.2 as that of 0.7.3.
  Rolling steward-run back reintroduces CVE-2026-75803.

## What it proves

CI runs every check on each pull request, on each push to `main` and nightly,
on GitHub-hosted amd64 runners. With the new product releases, everything
alpha.6 proved still holds: the core, task-auth and browser-admin end-to-end
tests run on every Kubernetes version in `kubernetes.tested`, install through
the reference install, and take every coordinate from the BOM. The task-auth
test runs the steward-run 0.7.5 action against Steward 0.3.3 and
github-oidc-exchange 0.7.4 with a real GitHub Actions OIDC token; the
browser-admin test checks that the apiserver carries the new projected
steward-run coordinates. See [the alpha.5 notes](2026.10.0-alpha.5.md#what-it-proves)
for what each test asserts, and [the alpha.6 notes](2026.10.0-alpha.6.md#what-it-proves)
for the registry mirror, built mode, CRD hook, Flux and backward
compatibility checks.

The other checks: every pinned digest resolves anonymously; Steward's and
mcp-gw's GitHub artifact attestations verify against the release workflow at
the release tag and the pinned commit; github-oidc-exchange's and
steward-run's cosign bundles verify, and their signed release manifests name
every pinned digest (and, for steward-run, exactly the action and workflow
coordinates Steward is configured with). See [verification](../verification.md).

## How to verify it yourself

From a checkout of this repository at the release tag, with the tools listed
in [verification](../verification.md):

```sh
scripts/validate-bom.sh
scripts/verify-digests.sh
GH_TOKEN=... scripts/verify-attestations.sh
scripts/verify-signatures.sh
tests/generate/run.sh
tests/built/run.sh
tests/hooks/run.sh
FLUX_SCHEMAS_DIR=... tests/flux/run.sh
```

`tests/generate/run.sh` needs the platform release tags in the checkout
(`git fetch --tags`) for its backward compatibility checks.
`verify-attestations.sh` needs a GitHub token, because `gh attestation
verify` reads attestations through the GitHub API; the others need no
credentials. The end-to-end tests need an amd64 Docker host; the task-auth
test also needs a GitHub Actions job that can request an OIDC token.

## What it does not do yet

- **No governed Task execution.** There is no governed profile: no runner
  scale set, Mint, SPIRE, sandbox or inference proxy is installed or tested
  ([#3](https://github.com/apelogic-ai/steward-platform/issues/3)).
- **No Task is admitted.** The task-auth test stops at
  `403 task_identity_unassociated`: associating a federated subject with a
  Steward user needs a browser session, and there is no non-browser path
  ([apelogic-ai/steward#179](https://github.com/apelogic-ai/steward/issues/179)).
- **No real Google login in CI.** The browser-admin test proves everything up
  to the redirect to Google; the sign-in, the session and every administrator
  action are covered only by the manual
  [first-admin runbook](../browser-admin/first-admin.md) and
  [walkthrough](../browser-admin/walkthrough.md).
- **amd64 only.** Steward images are linux/amd64 only
  ([apelogic-ai/steward#148](https://github.com/apelogic-ai/steward/issues/148)).
- **Google Workspace and GitHub.com are required** for browser login and
  governed use. Personal Google accounts, GitHub Enterprise Server and GitLab
  are not supported. See [prerequisites](../prerequisites.md).
- **mcp-gw is pinned but not exercised.** Nothing installs it until the
  governed profile exists.
- **Kubernetes 1.35 and 1.36 are not tested.** The fix for what failed on
  them is now pinned, but CI does not run them yet
  ([#34](https://github.com/apelogic-ai/steward-platform/issues/34)).
- **Built mode is not installed in CI.** Its generation and its refusals are
  tested; no end-to-end test installs built products, and nothing yet checks
  that running workloads use the lock digests
  ([#37](https://github.com/apelogic-ai/steward-platform/issues/37)).
- **The Flux output covers the production shape only.** Environments that use
  evaluation pieces (evaluation CA, PostgreSQL, edge CA or Gateway) get no
  Flux output, and the Flux reconcile job reconciles only the task-auth edge.
- **No automated BOM bumps or signed platform releases yet**
  ([#4](https://github.com/apelogic-ai/steward-platform/issues/4)).

## Known issues

- **The exchange's new network settings are not platform values.**
  github-oidc-exchange 0.7.4's `networkPolicy.dnsIpBlocks` (NodeLocal
  DNSCache), `apiServerCidrs`, `apiServerPorts`, `httpsEgressCidrs` and
  `extraEgress` (for example an HTTPS proxy), and
  `rolloutAutomation.reloader.enabled`, keep the chart defaults: API server
  and HTTPS egress to any address, no NodeLocal DNSCache addresses, no proxy
  rule, no Reloader. A cluster that needs other values has to patch the
  generated values until a values overlay exists
  ([#23](https://github.com/apelogic-ai/steward-platform/issues/23)).
- **Steward 0.3.3 names MCP-GW 0.4.9 through 0.5.0 for connection authority
  v2.** Its chart README was not updated for 0.5.1. mcp-gw 0.5.1's changelog
  lists no change to the provider connection lifecycle, so 0.5.1 is expected
  to implement the same `steward.connections.github/v2` contract
  **(inferred)**; nothing in this BOM exercises it until the governed profile
  exists.
- **Flux in built mode from a private registry needs a Kustomize patch.** The
  generated product `OCIRepository` objects carry no `secretRef`. See
  [fork and build from source](../fork-and-build.md#4-generate-in-built-mode).
- **The evaluation PostgreSQL chart takes no image pull Secret.** See
  [registry mirroring](../registry-mirroring.md#limits).
- **Changing profile in place** leaves the disabled releases installed, and
  task-auth to browser-admin fails on a `BackendTLSPolicy` ownership clash
  ([#33](https://github.com/apelogic-ai/steward-platform/issues/33)).
- **CI flake**: Steward can install before the evaluation CA is ready, so a
  browser-admin end-to-end run occasionally times out; a rerun passes
  ([#29](https://github.com/apelogic-ai/steward-platform/issues/29)).
