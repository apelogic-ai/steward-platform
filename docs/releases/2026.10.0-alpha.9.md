# Steward platform 2026.10.0-alpha.9

A pre-release of the Steward platform BOM that moves two products to their
current patch releases: Steward 0.3.5, a security patch, and mcp-gw 0.5.4,
pinned for the planned governed profile. github-oidc-exchange 0.7.5 and
steward-run 0.7.6 are unchanged. The platform itself (generator, helmfile,
Flux output, scripts, platform values schema) is unchanged from
[2026.10.0-alpha.8](2026.10.0-alpha.8.md). It is an alpha: the governed
profile, which runs agents, is not in it yet.

**No breaking changes for the core, task-auth and browser-admin profiles.**
Platform values written for alpha.8 validate unchanged and generate the same
install with the new product coordinates. Steward 0.3.5 removes unrestricted
Kubernetes user and group impersonation from the apiserver and controller
ClusterRoles ([Steward 0.3.5](#steward-035)); it has no migration and no
provider-profile transition, and keeps the v0.3.4 platform and
provider-profile contracts. mcp-gw 0.5.4 restores the Google Workspace tools
that 0.5.2 broke and recovers issuer keys without an agentgateway restart
([mcp-gw 0.5.4](#mcp-gw-054)).

[`bom/bom.json`](../../bom/bom.json) at this version is authoritative. The
tables below abbreviate digests to 12 hex characters for reading; install from
the full digests in the BOM, never from tags.

### What changed in each product

#### Steward 0.3.5

[Release notes](https://github.com/apelogic-ai/steward/releases/tag/v0.3.5),
[changelog](https://github.com/apelogic-ai/steward/blob/v0.3.5/CHANGELOG.md).

- **Security: no more Kubernetes user and group impersonation.** The
  apiserver and controller ClusterRoles no longer grant `impersonate` on
  `users` and `groups`. Both components write AgentRuntime resources as their
  own exact service-account identities, and the admission webhook still
  enforces the Envelope, grant, role-binding, principal-immutability and
  authority checks. A compromised Steward pod can no longer use its RBAC to
  impersonate another cluster principal
  ([chart README](https://github.com/apelogic-ai/steward/blob/v0.3.5/charts/steward/README.md),
  [installation guide](https://github.com/apelogic-ai/steward/blob/v0.3.5/docs/installation/installation-guide.md)).
- **A patch release with no database migration, no provider-profile
  transition and no chart value change.** The only chart template change
  removes those two RBAC rules, so the generated Steward values change only
  in image tags and digests. The release keeps the v0.3.4 platform and
  provider-profile contracts (provider-profile bundle 1.2.2), and rolling
  back to 0.3.4 needs no database rollback.
- **Rolling upgrade.** `helm upgrade` removes the obsolete impersonation
  rules; no manual RBAC action is needed. The changelog's upgrade note: while
  the pods roll, an old apiserver may briefly get `403` responses once the
  ClusterRole has changed, and a new apiserver served by the old controller
  webhook may have noncanonical user-runtime writes rejected, until both
  components run the same version. Retry after the apiserver and controller
  converge. Operators who added separate impersonation grants for these
  service accounts may remove them.

#### github-oidc-exchange 0.7.5 and steward-run 0.7.6

Unchanged from alpha.8; see
[the alpha.8 notes](2026.10.0-alpha.8.md#github-oidc-exchange-075). Steward's
projected `stewardRunRelease` is unchanged too.

#### mcp-gw 0.5.4

[Release](https://github.com/apelogic-ai/mcp-gw/releases/tag/v0.5.4),
[changelog](https://github.com/apelogic-ai/mcp-gw/blob/v0.5.4/CHANGELOG.md).
0.5.3 was tagged but never published: its release workflow stopped before it
published images, the chart or a GitHub release. 0.5.4 contains all 0.5.3
changes. From 0.5.1, the changes are:

- **Google Workspace tools work again.** The 0.5.2 chart and Compose defaults
  pointed `GWS_BINARY_PATH` at an obsolete path, so Google Workspace tool
  calls failed while the Pod reported Ready
  ([apelogic-ai/mcp-gw#100](https://github.com/apelogic-ai/mcp-gw/issues/100)).
  Every default now matches the image's `/usr/local/bin/gws`, the wrapper
  refuses to start on a non-executable CLI path, and the release smoke runs
  the real pinned CLI.
- **Issuer key recovery without a restart.** agentgateway retries a remote
  HOP-1 JWKS that was unavailable at startup and refreshes once, bounded, on
  an unknown key ID, so issuer recovery and signing-key rotation no longer
  need an agentgateway restart.
- **Reproducible images.** Wrapper apt packages resolve from a dated Ubuntu
  snapshot, base images are pinned by digest, the Google Workspace CLI is
  installed at build time against a committed checksum, and the unused
  Node.js runtime is gone. A build-from-source guide covers every image and
  the chart.
- **Supply chain.** First-party images and the chart are still verified with
  `gh attestation verify`, now bound to the tagged release workflow. The
  release also mirrors the official GitHub MCP Server image, unchanged, into
  `ghcr.io/apelogic-ai/mcp-gw-github-mcp-server`; its trust path is GitHub's
  upstream cosign signature plus digest equality, not an mcp-gw attestation.
  The chart default still references the upstream image, and the BOM pins
  neither.
- GitHub consent requires the HOP-1 email claim to match one of the user's
  verified GitHub emails (case-insensitive), and fails closed otherwise; this
  documents existing behavior.

No database migration, Secret format change, OAuth reconnect, chart value
rename or new required value. No profile installs mcp-gw.

## Upgrading from 2026.10.0-alpha.8

- **Platform values** from alpha.8 validate against the current schema
  unchanged and, with this BOM, generate exactly what alpha.8's generator
  generates; CI checks this for every committed environment of every
  platform release tag. Regenerating with this BOM changes only product
  coordinates: the Steward chart digest, the Steward image tags and digests,
  the `platformVersion` in the header comments and, in the task-auth and
  mirrored Flux output, the `steward-platform` `GitRepository` tag, to
  `2026.10.0-alpha.9`. github-oidc-exchange, `stewardRunRelease` and
  `charts/steward-edge` are unchanged.
- **Apply** with `helmfile --environment <env> --kube-context <context>
  sync`, or let Flux reconcile the regenerated objects. Steward adds no
  migration. During the roll, expect the transient `403` responses and
  rejected user-runtime writes described in
  [Steward 0.3.5](#steward-035); retry once the apiserver and controller run
  0.3.5. If you granted Steward's service accounts impersonation separately,
  you may remove that grant afterwards.
- **Steward governed users** (outside this BOM): no provider-profile
  transition. Deploy the 0.3.5 chart and images as one release unit.
- **mcp-gw** is not installed by any profile. If you installed the pinned
  0.5.1 yourself, read the 0.5.3 and 0.5.4 upgrade notes in the
  [mcp-gw changelog](https://github.com/apelogic-ai/mcp-gw/blob/v0.5.4/CHANGELOG.md)
  first: change or remove any Compose or Helm override that sets
  `GWS_BINARY_PATH=/app/node_modules/.bin/gws` (the wrapper now refuses to
  start on it), and, with GitHub OAuth, make sure the HOP-1 `emailClaim`
  resolves to a verified GitHub email.
- **Registry mirror.** Copy the new Steward and mcp-gw artifacts before
  regenerating: `scripts/mirror-list.sh` lists them, and
  `scripts/verify-digests.sh --mirror <platform-values>` checks the copy.
- **Built from source.** Rebuild Steward at the new release commit and write
  a new lock: the lock's versions, chart versions and commits must equal this
  BOM's, so an alpha.8 lock is refused.
- **Coming from a pre-platform install**: follow the
  [migration runbook](../upgrades/from-pre-platform.md) to the alpha.6
  product set, then the
  [alpha.7](2026.10.0-alpha.7.md#upgrading-from-2026100-alpha6) and
  [alpha.8](2026.10.0-alpha.8.md#upgrading-from-2026100-alpha7) upgrade
  notes, then this section.
- **Rolling back** to alpha.8 means generating from an alpha.8 checkout.
  Steward 0.3.5 to 0.3.4 needs no database rollback; restore the previous
  chart and image set as one release unit. It brings the impersonation rules
  back.

## What it proves

CI runs every check on each pull request, on each push to `main` and nightly,
on GitHub-hosted amd64 runners. With the new product releases, everything
alpha.8 proved still holds: the core, task-auth and browser-admin end-to-end
tests run on every Kubernetes version in `kubernetes.tested`, install through
the reference install, and take every coordinate from the BOM. They install
Steward 0.3.5 with its reduced ClusterRoles; the task-auth test runs the
steward-run 0.7.6 action against Steward 0.3.5 and github-oidc-exchange 0.7.5
with a real GitHub Actions OIDC token, and asserts the same exchange audit
reasons and the same `403 task_identity_unassociated` answer. See
[the alpha.5 notes](2026.10.0-alpha.5.md#what-it-proves) for what each test
asserts, and [the alpha.6 notes](2026.10.0-alpha.6.md#what-it-proves) for the
registry mirror, built mode, CRD hook, Flux and backward compatibility checks.

The other checks: every pinned digest resolves anonymously; Steward's and
mcp-gw's GitHub artifact attestations verify against the release workflow at
the release tag and the pinned commit; github-oidc-exchange's and
steward-run's cosign bundles verify, and their signed release manifests name
every pinned digest (and, for steward-run, exactly the action and workflow
coordinates Steward is configured with). See [verification](../verification.md).

## How to verify it yourself

From a checkout of this repository at the release tag, with the tools listed
in [verification](../verification.md):

```sh
scripts/validate-bom.sh
scripts/verify-digests.sh
GH_TOKEN=... scripts/verify-attestations.sh
scripts/verify-signatures.sh
tests/generate/run.sh
tests/built/run.sh
tests/hooks/run.sh
FLUX_SCHEMAS_DIR=... tests/flux/run.sh
```

`tests/generate/run.sh` needs the platform release tags in the checkout
(`git fetch --tags`) for its backward compatibility checks.
`verify-attestations.sh` needs a GitHub token, because `gh attestation
verify` reads attestations through the GitHub API; the others need no
credentials. The end-to-end tests need an amd64 Docker host; the task-auth
test also needs a GitHub Actions job that can request an OIDC token.

## What it does not do yet

- **No governed Task execution.** There is no governed profile: no runner
  scale set, Mint, SPIRE, sandbox or inference proxy is installed or tested
  ([#3](https://github.com/apelogic-ai/steward-platform/issues/3)).
- **No Task is admitted.** The task-auth test stops at
  `403 task_identity_unassociated`: associating a federated subject with a
  Steward user needs a browser session, and there is no non-browser path
  ([apelogic-ai/steward#179](https://github.com/apelogic-ai/steward/issues/179)).
- **No real Google login in CI.** The browser-admin test proves everything up
  to the redirect to Google; the sign-in, the session and every administrator
  action are covered only by the manual
  [first-admin runbook](../browser-admin/first-admin.md) and
  [walkthrough](../browser-admin/walkthrough.md).
- **amd64 only.** Steward images are linux/amd64 only
  ([apelogic-ai/steward#148](https://github.com/apelogic-ai/steward/issues/148)).
- **Google Workspace and GitHub.com are required** for browser login and
  governed use. Personal Google accounts, GitHub Enterprise Server and GitLab
  are not supported. See [prerequisites](../prerequisites.md).
- **mcp-gw is pinned but not exercised.** Nothing installs it until the
  governed profile exists.
- **Kubernetes 1.35 and 1.36 are not tested**
  ([#34](https://github.com/apelogic-ai/steward-platform/issues/34)).
- **Built mode is not installed in CI.** Its generation and its refusals are
  tested; no end-to-end test installs built products, and nothing yet checks
  that running workloads use the lock digests
  ([#37](https://github.com/apelogic-ai/steward-platform/issues/37)).
- **The Flux output covers the production shape only.** Environments that use
  evaluation pieces (evaluation CA, PostgreSQL, edge CA or Gateway) get no
  Flux output, and the Flux reconcile job reconciles only the task-auth edge.
- **No automated BOM bumps or signed platform releases yet**
  ([#4](https://github.com/apelogic-ai/steward-platform/issues/4)).

## Known issues

- **Steward names an older tested mcp-gw.** Steward 0.3.5's
  [installation guide](https://github.com/apelogic-ai/steward/blob/v0.3.5/docs/installation/installation-guide.md#tested-versions-and-integration-boundaries)
  still lists MCP-GW 0.5.1 as tested for the
  `steward.connections.github/v2` authority contract. The mcp-gw changelog
  lists no authority contract change from 0.5.1 to 0.5.4. No profile
  installs mcp-gw, so this matters only when the governed profile arrives.
- **The exchange's network and JWKS settings are not platform values.**
  github-oidc-exchange's `networkPolicy.dnsIpBlocks` (NodeLocal DNSCache),
  `apiServerCidrs`, `apiServerPorts`, `httpsEgressCidrs` and `extraEgress`
  (for example an HTTPS proxy), `rolloutAutomation.reloader.enabled` and
  `config.githubJwksMaxStalenessSeconds` keep the chart defaults. A cluster
  that needs other values has to patch the generated values until a values
  overlay exists
  ([#23](https://github.com/apelogic-ai/steward-platform/issues/23)).
- **steward-run's guide lags the exchange.** steward-run 0.7.6's installation
  guide still says policy v6 has no workflow-ref or workflow-SHA selector;
  github-oidc-exchange 0.7.5 adds them. The exchange's
  [integration guide](https://github.com/apelogic-ai/github-oidc-exchange/blob/v0.7.5/docs/integration.md)
  is the authority for the policy.
- **Flux in built mode from a private registry needs a Kustomize patch.** The
  generated product `OCIRepository` objects carry no `secretRef`. See
  [fork and build from source](../fork-and-build.md#4-generate-in-built-mode).
- **The evaluation PostgreSQL chart takes no image pull Secret.** See
  [registry mirroring](../registry-mirroring.md#limits).
- **Changing profile in place** leaves the disabled releases installed, and
  task-auth to browser-admin fails on a `BackendTLSPolicy` ownership clash
  ([#33](https://github.com/apelogic-ai/steward-platform/issues/33)).
- **CI flake**: Steward can install before the evaluation CA is ready, so a
  browser-admin end-to-end run occasionally times out; a rerun passes
  ([#29](https://github.com/apelogic-ai/steward-platform/issues/29)).

Resolved since alpha.8: the pinned mcp-gw is past the 0.5.2 Google Workspace
regression ([apelogic-ai/mcp-gw#100](https://github.com/apelogic-ai/mcp-gw/issues/100),
closed).
