# Steward platform 2026.10.0-alpha.8

A pre-release of the Steward platform BOM that moves three products to their
current patch releases: Steward 0.3.4, github-oidc-exchange 0.7.5 and
steward-run 0.7.6. mcp-gw, pinned for the planned governed profile, stays at
0.5.1 ([why](#mcp-gw-051)). The platform itself (generator, helmfile, Flux
output, scripts, platform values schema) is unchanged from
[2026.10.0-alpha.7](2026.10.0-alpha.7.md). It is an alpha: the governed
profile, which runs agents, is not in it yet.

**No breaking changes for the core, task-auth and browser-admin profiles.**
Platform values written for alpha.7 validate unchanged and generate the same
install with the new product coordinates. Steward 0.3.4 has one **Required
action**, for installs that enable Steward's governed execution (none of the
profiles in this BOM does): the `steward-workflows` namespace must exist and
be listed in `runtimeNamespaces` ([Steward 0.3.4](#steward-034)). It also
fixes both Steward 0.3.3 known issues and restores the HyperShell branding in
the web UI. steward-run 0.7.6 publishes a vendorable reusable workflow for
callers of a private fork, and github-oidc-exchange 0.7.5 adds opt-in
owner-wide admission to policy v6.

[`bom/bom.json`](../../bom/bom.json) at this version is authoritative. The
tables below abbreviate digests to 12 hex characters for reading; install from
the full digests in the BOM, never from tags.

### What changed in each product

#### Steward 0.3.4

[Release notes](https://github.com/apelogic-ai/steward/releases/tag/v0.3.4),
[changelog](https://github.com/apelogic-ai/steward/blob/v0.3.4/CHANGELOG.md).

- **A patch release with no database migration and no chart default
  change.** The only template change is the new check below, so the generated
  Steward values change only in image tags and digests. Rolling back to 0.3.3
  needs no database rollback.
- **Required action, for execution-enabled installs.** Versioned Workflow
  Tasks run in the fixed `steward-workflows` namespace. Before every
  execution-enabled upgrade to 0.3.4, create that namespace and add it to
  `runtimeNamespaces`; the chart now refuses `execution.enabled: true`
  without it, and values copied from Steward's earlier `[steward-tasks]`
  example must be updated first
  ([apelogic-ai/steward#207](https://github.com/apelogic-ai/steward/issues/207);
  [chart README](https://github.com/apelogic-ai/steward/blob/v0.3.4/charts/steward/README.md)).
  The profiles in this BOM run Steward with `execution.enabled: false` and set
  no `runtimeNamespaces`, so they need nothing; the governed profile will have
  to include the namespace.
- **The Steward 0.3.3 known issues are fixed.** Both affected only
  execution-enabled installs:
  - The 0.3.3 apiserver crash-looped at startup when
    `config.apiserver.anthropicInferenceEndpoint` was empty, even with no
    Claude binding, so 0.3.3 needed a placeholder value. 0.3.4 requires the
    field only when a `claude-code-v1` binding is active
    ([apelogic-ai/steward#212](https://github.com/apelogic-ai/steward/issues/212)).
  - The 0.3.3 preflight required an HTTPS LiteLLM management URL
    (`config.controller.litellmUrl`), while the chart's NetworkPolicy allows
    only the in-cluster LiteLLM Service over HTTP. The 0.3.4 preflight accepts
    plain HTTP for exactly `litellm.<namespace>.svc` (or
    `.svc.cluster.local`) on port 4000, which the generated NetworkPolicy
    authorizes. An external HTTPS origin still needs an operator-owned,
    narrowly scoped egress rule
    ([apelogic-ai/steward#213](https://github.com/apelogic-ai/steward/issues/213);
    [platform preflight](https://github.com/apelogic-ai/steward/blob/v0.3.4/docs/installation/platform-preflight.md)).
  - Also fixed: the apiserver no longer fails to start when the onboarding
    sample Workflow names an agent that the current execution bindings no
    longer advertise; it logs a warning and hides the sample
    ([apelogic-ai/steward#209](https://github.com/apelogic-ai/steward/issues/209)).
- **HyperShell branding is back in the web UI.** Page titles, logo, favicon
  and product-facing copy say HyperShell again
  ([apelogic-ai/steward#200](https://github.com/apelogic-ai/steward/issues/200)).
  Package, chart, image, CLI and API names stay `steward`, so nothing in the
  platform values or the generated output changes. Browser-admin users see
  the new name. The web UI's theme cookie is renamed, so a saved light or dark
  preference resets once **(inferred from the source change)**.
- **Governed execution only** (outside this BOM): provider-profile bundle
  1.2.2 adds `DELETE` to the MCP transport for session close, with an exact
  1.2.1 to 1.2.2 transition; the preflight checks optional ARC installations,
  the Workflow runtime namespace, custom Mint audiences and more blocked
  CIDRs. Steward now documents MCP-GW 0.5.1, LiteLLM v1.93.0 and SPIRE chart
  0.29.0 as tested, and asks the public edge to allow at least 60 seconds for
  `/admin/api/v1/connections/*`.

#### github-oidc-exchange 0.7.5

[Release notes](https://github.com/apelogic-ai/github-oidc-exchange/blob/v0.7.5/docs/releases/v0.7.5.md),
[upgrade guide](https://github.com/apelogic-ai/github-oidc-exchange/blob/v0.7.5/docs/upgrade-v0.7.5.md).
Non-breaking: routes, audiences, token lifetimes, policy versions, output
contracts, the default v5 policy, the signer (`release.yml` on `main`), the
release manifest and the signature asset names
(`public-image-signature.sigstore.json`,
`public-chart-signature.sigstore.json`) are unchanged.

- **Opt-in owner-wide admission (policy v6).** A v6 repository rule may set
  `repository_id` to `"*"` for one numeric `owner_id`, admitting every
  repository of that owner, including repositories created later. The rule's
  subject, event, ref and workflow selectors still apply; exact repository
  rules stay the default and may not overlap an owner-wide rule for the same
  owner, and the issued token's source provenance always names the concrete
  repository ID. Upgrading changes no existing rule. See
  [opt in to v6](https://github.com/apelogic-ai/github-oidc-exchange/blob/v0.7.5/docs/integration.md#opt-in-to-v6-and-steward-task-v3).
- **Reusable-workflow selectors (policy v6).** Optional `job_workflow_refs`
  and `job_workflow_shas` admit only exact reusable-workflow references and
  commits. The task-auth end-to-end test does not use them or owner-wide
  rules: its policy is the same as with 0.7.4 (one exact repository, subject,
  event and ref).
- **Readiness and observability.** `/readyz` now also fails when the cached
  GitHub JWKS is older than `config.githubJwksMaxStalenessSeconds` (six hours
  by default) or the Kubernetes Lease API is unreachable, and returns stable
  check names such as `github_jwks` and `replay_ledger`. Cached GitHub keys
  stay usable through shorter outages, refreshed in the background. New
  metrics (`github_oidc_exchange_jwks_age_seconds`,
  `github_oidc_exchange_jwks_refresh_failures_total`, an exchange latency
  histogram) and an
  [operator observability contract](https://github.com/apelogic-ai/github-oidc-exchange/blob/v0.7.5/docs/operator-observability-contract-v1.md)
  document the audit events and reasons, which are unchanged: the task-auth
  test's audit assertions (`exchange_issued`, `exchange_replayed`,
  `exchange_denied` and their reasons) hold as before.
- **One new chart value, left at its default.** The generator does not set
  `config.githubJwksMaxStalenessSeconds`, so the chart default (21600
  seconds) applies; the generated values render with the 0.7.5 chart schema,
  which requires it.

#### steward-run 0.7.6

[Release notes](https://github.com/apelogic-ai/steward-run/blob/v0.7.6/docs/release-notes-v0.7.6.md),
[changelog](https://github.com/apelogic-ai/steward-run/blob/v0.7.6/CHANGELOG.md).

- **A vendorable reusable workflow.** The release publishes a fully rendered
  `steward-task-vendored.yml`, its template and the deterministic renderer,
  bound by `SHA256SUMS` and the signed manifest. A repository that must call
  a private steward-run fork copies it into its own `.github/workflows/`: it
  calls the manifest's exact `workflowRepository@actionCommit` directly, with
  no internal checkout of the private repository and no PAT or checkout token.
  Steward does not yet render the local `uses:` reference, so callers change
  that one line by hand
  ([apelogic-ai/steward#218](https://github.com/apelogic-ai/steward/issues/218)).
  The vendored workflow requires the task to write at least one file under
  `out/`. See
  [private fork consumed by another repository](https://github.com/apelogic-ai/steward-run/blob/v0.7.6/docs/installation.md#private-fork-consumed-by-another-repository).
- **Clearer exchange failures.** Identity exchange `400`, `401` and `403`
  responses are no longer retried or reported as `transport`: the action
  fails after one attempt with `failure-category` `authentication` or
  `authorization`, the HTTP status and a diagnostic that points at the
  policy's repository, subject, event and ref selectors. `429`, `5xx` and
  network failures are still retried. Action inputs are unchanged; the
  task-auth end-to-end test runs the action at the new commit with the same
  inputs.
- **Release integrity.** The runner image resolves its Ubuntu packages from a
  dated immutable snapshot, and the governed job container is signed before
  the tag and promoted unchanged, so the signed manifest's `image` is exactly
  the digest `steward-task.yml` embeds.
- **Manifest coordinates.** Still schema 3, with the tag commit as both
  `workflowCommit` and `actionCommit` (`fbfd6c093e6d`). Steward's
  `config.apiserver.stewardRunRelease`, which the generator projects from the
  BOM for browser-admin, changes in `version`, `workflowCommit`,
  `actionCommit` and `governedJobContainerImage`; `verify-signatures.sh`
  checks that the projection equals the signed manifest field for field. The
  signer is `portable-release.yml` at the release tag, so the BOM's
  `certificateIdentity` is now `...portable-release.yml@refs/tags/v0.7.6`.

## Upgrading from 2026.10.0-alpha.7

- **Platform values** from alpha.7 validate against the current schema
  unchanged and, with this BOM, generate exactly what alpha.7's generator
  generates; CI checks this for every committed environment of every
  platform release tag. Regenerating with this BOM changes only product
  coordinates: the product chart digests, the image tags and digests,
  Steward's `stewardRunRelease` (browser-admin), the `platformVersion` in the
  header comments and, in the task-auth Flux output, the `steward-platform`
  `GitRepository` tag, to `2026.10.0-alpha.8`. `charts/steward-edge` is
  unchanged.
- **Apply** with `helmfile --environment <env> --kube-context <context>
  sync`, or let Flux reconcile the regenerated objects. Steward adds no
  migration. github-oidc-exchange rolls its pods to the new image; its
  readiness now also depends on a fresh GitHub JWKS and the Lease API, so
  alert on `/readyz` failures and the new JWKS metrics.
- **Steward governed users** (outside this BOM), before the Helm upgrade to
  0.3.4:
  - **Required action:** create the `steward-workflows` namespace and add it
    to `runtimeNamespaces`, or `helm upgrade` fails.
  - Stop the controller and apiserver, enable OpenShell's
    `providers_v2_enabled`, and apply the provider-profile bundle 1.2.1 to
    1.2.2 transition from a checkout of the `v0.3.4` tag (from 0.3.2, run the
    1.2.0 to 1.2.1 and 1.2.1 to 1.2.2 transitions in order, with no Helm
    upgrade to 0.3.3 in between). Rerun the platform preflight and use the
    regenerated values and profile digests. See the
    [bundle guide](https://github.com/apelogic-ai/steward/blob/v0.3.4/config/provider-profile-bundle/v1.2.2/README.md)
    and the [Steward 0.3.4 changelog](https://github.com/apelogic-ai/steward/blob/v0.3.4/CHANGELOG.md).
  - The 0.3.3 workarounds can go: a Codex-only install no longer needs a
    placeholder `anthropicInferenceEndpoint`, and the LiteLLM management URL
    can be the in-cluster `http://litellm.<namespace>.svc:4000` instead of an
    HTTPS front.
- **steward-run callers.** Repositories that pin the steward-run action or
  reusable workflow by commit, including workflows Steward generated from the
  previous `stewardRunRelease`, keep running 0.7.5 until they are updated to
  commit `fbfd6c093e6d`. steward-run asks for the action and workflow commit,
  image digest, chart and vendored workflow to move together as one verified
  unit, followed by the read-only ARC preflight and one governed delivery
  test. Private-fork callers can switch to the vendored workflow.
- **github-oidc-exchange policies** need no change. Owner-wide rules and the
  reusable-workflow selectors are opt-in; add them only as a reviewed policy
  change with a new `rolloutRevisions.githubPolicy`.
- **mcp-gw** is unchanged.
- **Registry mirror.** Copy the new product artifacts before regenerating:
  `scripts/mirror-list.sh` lists them, and `scripts/verify-digests.sh --mirror
  <platform-values>` checks the copy.
- **Built from source.** Rebuild Steward and github-oidc-exchange at the new
  release commits and write a new lock: the lock's versions, chart versions
  and commits must equal this BOM's, so an alpha.7 lock is refused.
- **Coming from a pre-platform install**: follow the
  [migration runbook](../upgrades/from-pre-platform.md) to the alpha.6
  product set, then the
  [alpha.7 upgrade notes](2026.10.0-alpha.7.md#upgrading-from-2026100-alpha6),
  then this section.
- **Rolling back** to alpha.7 means generating from an alpha.7 checkout.
  Steward 0.3.4 to 0.3.3 needs no database rollback, but brings back the
  0.3.3 known issues for governed installs; restore the previous
  provider-profile bundle as one stopped-consumer unit. github-oidc-exchange
  documents 0.7.4 as the rollback pair of 0.7.5; roll back the application,
  chart and policy together. Rolling steward-run back to 0.7.5 restores the
  old exchange `401` retry behavior.

## What it proves

CI runs every check on each pull request, on each push to `main` and nightly,
on GitHub-hosted amd64 runners. With the new product releases, everything
alpha.7 proved still holds: the core, task-auth and browser-admin end-to-end
tests run on every Kubernetes version in `kubernetes.tested`, install through
the reference install, and take every coordinate from the BOM. The task-auth
test runs the steward-run 0.7.6 action against Steward 0.3.4 and
github-oidc-exchange 0.7.5 with a real GitHub Actions OIDC token, and asserts
the same exchange audit reasons and the same `403 task_identity_unassociated`
answer; the browser-admin test checks that the apiserver carries the new
projected steward-run coordinates. See
[the alpha.5 notes](2026.10.0-alpha.5.md#what-it-proves) for what each test
asserts, and [the alpha.6 notes](2026.10.0-alpha.6.md#what-it-proves) for the
registry mirror, built mode, CRD hook, Flux and backward compatibility checks.

The other checks: every pinned digest resolves anonymously; Steward's and
mcp-gw's GitHub artifact attestations verify against the release workflow at
the release tag and the pinned commit; github-oidc-exchange's and
steward-run's cosign bundles verify, and their signed release manifests name
every pinned digest (and, for steward-run, exactly the action and workflow
coordinates Steward is configured with). See [verification](../verification.md).

## How to verify it yourself

From a checkout of this repository at the release tag, with the tools listed
in [verification](../verification.md):

```sh
scripts/validate-bom.sh
scripts/verify-digests.sh
GH_TOKEN=... scripts/verify-attestations.sh
scripts/verify-signatures.sh
tests/generate/run.sh
tests/built/run.sh
tests/hooks/run.sh
FLUX_SCHEMAS_DIR=... tests/flux/run.sh
```

`tests/generate/run.sh` needs the platform release tags in the checkout
(`git fetch --tags`) for its backward compatibility checks.
`verify-attestations.sh` needs a GitHub token, because `gh attestation
verify` reads attestations through the GitHub API; the others need no
credentials. The end-to-end tests need an amd64 Docker host; the task-auth
test also needs a GitHub Actions job that can request an OIDC token.

## What it does not do yet

- **No governed Task execution.** There is no governed profile: no runner
  scale set, Mint, SPIRE, sandbox or inference proxy is installed or tested
  ([#3](https://github.com/apelogic-ai/steward-platform/issues/3)).
- **No Task is admitted.** The task-auth test stops at
  `403 task_identity_unassociated`: associating a federated subject with a
  Steward user needs a browser session, and there is no non-browser path
  ([apelogic-ai/steward#179](https://github.com/apelogic-ai/steward/issues/179)).
- **No real Google login in CI.** The browser-admin test proves everything up
  to the redirect to Google; the sign-in, the session and every administrator
  action are covered only by the manual
  [first-admin runbook](../browser-admin/first-admin.md) and
  [walkthrough](../browser-admin/walkthrough.md).
- **amd64 only.** Steward images are linux/amd64 only
  ([apelogic-ai/steward#148](https://github.com/apelogic-ai/steward/issues/148)).
- **Google Workspace and GitHub.com are required** for browser login and
  governed use. Personal Google accounts, GitHub Enterprise Server and GitLab
  are not supported. See [prerequisites](../prerequisites.md).
- **mcp-gw is pinned but not exercised.** Nothing installs it until the
  governed profile exists.
- **Kubernetes 1.35 and 1.36 are not tested**
  ([#34](https://github.com/apelogic-ai/steward-platform/issues/34)).
- **Built mode is not installed in CI.** Its generation and its refusals are
  tested; no end-to-end test installs built products, and nothing yet checks
  that running workloads use the lock digests
  ([#37](https://github.com/apelogic-ai/steward-platform/issues/37)).
- **The Flux output covers the production shape only.** Environments that use
  evaluation pieces (evaluation CA, PostgreSQL, edge CA or Gateway) get no
  Flux output, and the Flux reconcile job reconciles only the task-auth edge.
- **No automated BOM bumps or signed platform releases yet**
  ([#4](https://github.com/apelogic-ai/steward-platform/issues/4)).

## Known issues

- **The exchange's network and JWKS settings are not platform values.**
  github-oidc-exchange's `networkPolicy.dnsIpBlocks` (NodeLocal DNSCache),
  `apiServerCidrs`, `apiServerPorts`, `httpsEgressCidrs` and `extraEgress`
  (for example an HTTPS proxy), `rolloutAutomation.reloader.enabled`, and now
  `config.githubJwksMaxStalenessSeconds`, keep the chart defaults. A cluster
  that needs other values has to patch the generated values until a values
  overlay exists
  ([#23](https://github.com/apelogic-ai/steward-platform/issues/23)).
- **steward-run's guide lags the exchange.** steward-run 0.7.6's installation
  guide still says policy v6 has no workflow-ref or workflow-SHA selector;
  github-oidc-exchange 0.7.5 adds them. The exchange's
  [integration guide](https://github.com/apelogic-ai/github-oidc-exchange/blob/v0.7.5/docs/integration.md)
  is the authority for the policy.
- **Flux in built mode from a private registry needs a Kustomize patch.** The
  generated product `OCIRepository` objects carry no `secretRef`. See
  [fork and build from source](../fork-and-build.md#4-generate-in-built-mode).
- **The evaluation PostgreSQL chart takes no image pull Secret.** See
  [registry mirroring](../registry-mirroring.md#limits).
- **Changing profile in place** leaves the disabled releases installed, and
  task-auth to browser-admin fails on a `BackendTLSPolicy` ownership clash
  ([#33](https://github.com/apelogic-ai/steward-platform/issues/33)).
- **CI flake**: Steward can install before the evaluation CA is ready, so a
  browser-admin end-to-end run occasionally times out; a rerun passes
  ([#29](https://github.com/apelogic-ai/steward-platform/issues/29)).

Resolved since alpha.7: Steward 0.3.4 documents MCP-GW 0.5.1 for connection
authority v2, where 0.3.3 named only 0.4.9 through 0.5.0.
