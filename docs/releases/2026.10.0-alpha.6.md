# Steward platform 2026.10.0-alpha.6

A pre-release of the Steward platform BOM that adds install options and a
safety fix around the same product releases as
[2026.10.0-alpha.5](2026.10.0-alpha.5.md): installing from a registry
mirror, installing products built from source, Flux output for every
implemented profile, PostgreSQL 17 as a tested version, and a fix that keeps
the helmfile's CRD hook on the releases' cluster. It is an alpha: the
governed profile, which runs agents, is not in it yet.

**No breaking changes, and the same product versions as alpha.5.** Every
product version, chart and image digest, every default dependency pin and the
tested Kubernetes versions are unchanged. The one pin added is PostgreSQL
17.11, as a second tested version for evaluation. Platform values written for
alpha.5 validate unchanged and generate the same install; every new platform
values field is optional.

[`bom/bom.json`](../../bom/bom.json) at this version is authoritative. The
tables below abbreviate digests to 12 hex characters for reading; install from
the full digests in the BOM, never from tags.

## What's new

- **Registry mirror.** The optional platform values block `registry` pulls
  each artifact class from your own mirror: product images and charts,
  dependency images and charts, and the Git sources and CRD manifests of the
  Flux output and the helmfile. Image pull Secrets and Flux credentials are
  referenced by name. Tags and digests stay the BOM's.
  [`scripts/mirror-list.sh`](../../scripts/mirror-list.sh) lists everything the
  platform pulls, for copying, and `scripts/verify-digests.sh --mirror
  PLATFORM_VALUES` checks the copy with your credentials: every mirrored
  artifact must resolve at its BOM digest. A new
  [`examples/flux/mirrored`](../../examples/flux/mirrored/README.md) example
  shows the Flux output from a mirror. See
  [registry mirroring](../registry-mirroring.md).
- **Products built from source.** The optional platform values block
  `artifacts` (`source: built`, `builtLock`) installs each deployed product's
  chart and images from a built-artifacts lock
  ([schema](../../schemas/built-lock/v1.schema.json)). The lock records
  products you built from source at the BOM's release commits, or from a fork
  with `allowSourceDrift`, and pushed to your registry. The generator checks
  the lock against the BOM and lists every missing chart or image.
  [`scripts/built-lock-from-digests.sh`](../../scripts/built-lock-from-digests.sh)
  writes a lock and
  [`scripts/verify-built-lock.sh`](../../scripts/verify-built-lock.sh) checks
  it. `verify-digests.sh`, `verify-attestations.sh` and
  `verify-signatures.sh` take `--built-lock`, and report built products as
  checked against the lock or as skipped, never as upstream-verified. Built
  mode combines with a registry mirror for everything except the products. See
  [fork and build from source](../fork-and-build.md).
- **Safety fix: the CRD hook targets the releases' kube context.** In
  alpha.5, the helmfile's `envoy-gateway` presync hook
  (`scripts/apply-manifests.sh`) ignored helmfile's `--kube-context`. Unless
  `PLATFORM_KUBE_CONTEXT` was set, it server-side applied the Gateway API and
  Envoy Gateway CRDs to the current kubeconfig context. So
  `helmfile --kube-context A sync` with current context B wrote the CRDs to
  cluster B and installed the releases on cluster A. The hook now receives
  the release's kube context from helmfile and names it on every `kubectl`
  call. It refuses to run wherever the CRDs and the releases could land on
  different clusters. This affects the task-auth and browser-admin profiles,
  whose helmfile runs the hook. See
  [the CRD hook and the kube context](../../helmfile/README.md#the-crd-hook-and-the-kube-context).
- **Flux output for task-auth and browser-admin.** The generator now writes
  Flux objects for the production shape of every implemented profile, not
  only core: new examples
  [`examples/flux/task-auth`](../../examples/flux/task-auth/README.md) and
  [`examples/flux/browser-admin`](../../examples/flux/browser-admin/README.md).
  The helmfile's CRD hook becomes Flux `Kustomization`s from each manifest's
  pinned `fluxSource`. `charts/steward-edge` (task-auth) is built from this
  repository at the tag of the `platformVersion`, so the task-auth Flux
  output of this BOM needs the `2026.10.0-alpha.6` tag.
- **PostgreSQL 17 tested.** PostgreSQL 17.11 is pinned next to 16.14, and the
  core end-to-end test runs on both. The optional platform values field
  `database.evaluationVersion` picks the version the evaluation database
  runs; the default stays 16.14. See
  [prerequisites](../prerequisites.md#postgresql).
- **Documentation.** A
  [migration runbook](../upgrades/from-pre-platform.md) from pre-platform
  (0.2.6-era) installs to this product set, and the
  [known security limitations](../prerequisites.md#known-security-limitations)
  of the browser-admin profile, with interim mitigations.

## Upgrading from 2026.10.0-alpha.5

No change is required. The products, their digests and the default
dependency pins are the same, so an upgrade changes no workload.

- **Platform values** from alpha.5 validate against the current schema
  unchanged. With this BOM they generate exactly what alpha.5's generator
  generates; CI checks this for every committed environment of every platform
  release tag. Regenerating changes only the `platformVersion` in the header
  comments and, in the task-auth Flux output, the `steward-platform`
  `GitRepository` tag, to `2026.10.0-alpha.6`. `charts/steward-edge` itself
  is unchanged since alpha.5.
- **helmfile: pass `--kube-context`.** It is now the recommended form, for
  example `helmfile --environment <env> --kube-context <context> sync`, or set
  `HELMFILE_KUBE_CONTEXT`. The hook resolves its context in this order:
  1. helmfile's context for the release: `--kube-context`, else
     `HELMFILE_KUBE_CONTEXT`, else a `kubeContext` on the release or the
     helmfile environment;
  2. `PLATFORM_KUBE_CONTEXT`, which still works: with a context from step 1
     the two must be equal, and without one it must equal the current
     kubeconfig context;
  3. neither: the current kubeconfig context, where Helm installs the
     releases too, named explicitly, with a notice.

  The hook refuses when `PLATFORM_KUBE_CONTEXT` names a different context,
  when the context is not in the kubeconfig, and when helmfile was run with
  `--kubeconfig`, which helmfile does not pass to hooks; select the file with
  `KUBECONFIG` instead. The documented invocations, with or without
  `--kube-context` or `PLATFORM_KUBE_CONTEXT`, keep working.
- **Check for stray CRDs** if you ran a task-auth or browser-admin
  `helmfile sync` under alpha.5 with `--kube-context` naming a cluster other
  than the current context. That cluster may hold Gateway API and Envoy
  Gateway CRDs you did not intend:
  `kubectl --context <that context> get crds | grep -E 'gateway.networking.k8s.io|gateway.envoyproxy.io'`.
- **Mirror and built mode** are opt-in: without a `registry` or `artifacts`
  block, the generated output is byte-identical to before.

## What it proves

CI runs every check on each pull request, on each push to `main` and nightly,
on GitHub-hosted amd64 runners. Everything alpha.5 proved still holds: the
core, task-auth and browser-admin end-to-end tests run on every Kubernetes
version in `kubernetes.tested`, install through the reference install, and
take every coordinate from the BOM. See
[the alpha.5 notes](2026.10.0-alpha.5.md#what-it-proves) for what each test
asserts. New in alpha.6:

- **PostgreSQL 17.11**: one more core end-to-end run, on Kubernetes 1.34.3,
  checks the exact server version and applies every Steward migration.
- **Registry mirror**: one more core end-to-end run, on Kubernetes 1.34.3,
  runs a local registry, copies what the install pulls with the mirror list,
  checks the copy with `verify-digests.sh --mirror`, installs from the mirror
  with the helmfile, and asserts that the pods run the BOM digests from the
  mirror host. The generator and Flux checks cover the mirrored environment
  and [`examples/flux/mirrored`](../../examples/flux/mirrored/README.md).
- **Built mode**: `tests/built/run.sh` generates every committed environment
  in built mode with the example lock. Built mode must replace exactly the
  product chart and image references and nothing else, and must refuse a lock
  that misses or mismatches an entry. With `artifacts.source: bom`, or with a
  lock of the BOM's own references, the output must equal BOM mode.
- **CRD hook**: `tests/hooks/run.sh` runs the hook with stand-in `kubectl`,
  `curl` and `helm`, with a current context that is a different cluster. The
  hook must apply to exactly one named context, or refuse before downloading
  anything. Through the pinned helmfile, `--kube-context` and
  `HELMFILE_KUBE_CONTEXT` must reach the hook.
- **Flux**: `tests/flux/run.sh` checks all four examples against the BOM, the
  helmfile and the pinned Flux schemas. It also checks that each CRD
  `fluxSource`, at its pin, holds exactly the objects of the BOM manifest. The
  Flux reconcile job reconciles the task-auth edge (CRD `Kustomization`s,
  Envoy Gateway and `steward-edge`) with the pinned Flux release in kind.
- **Backward compatibility**: the platform values of every platform release
  tag validate and generate byte-identically to that tag's own generator.

See [verification](../verification.md).

## How to verify it yourself

From a checkout of this repository at the release tag, with the tools listed
in [verification](../verification.md):

```sh
scripts/validate-bom.sh
scripts/verify-digests.sh
GH_TOKEN=... scripts/verify-attestations.sh
scripts/verify-signatures.sh
tests/generate/run.sh
tests/built/run.sh
tests/hooks/run.sh
FLUX_SCHEMAS_DIR=... tests/flux/run.sh
```

`tests/generate/run.sh` needs the platform release tags in the checkout
(`git fetch --tags`) for its backward compatibility checks.
`verify-attestations.sh` needs a GitHub token, because `gh attestation
verify` reads attestations through the GitHub API; the others need no
credentials. The end-to-end tests need an amd64 Docker host; the task-auth
test also needs a GitHub Actions job that can request an OIDC token.

To check your own copies: `scripts/verify-digests.sh --mirror
<platform-values>` for a registry mirror, and
`scripts/verify-built-lock.sh --profile <profile> <lock>` with
`--built-lock <lock>` on the verify scripts for products built from source.

## What it does not do yet

- **No governed Task execution.** There is no governed profile: no runner
  scale set, Mint, SPIRE, sandbox or inference proxy is installed or tested
  ([#3](https://github.com/apelogic-ai/steward-platform/issues/3)).
- **No Task is admitted.** The task-auth test stops at
  `403 task_identity_unassociated`: associating a federated subject with a
  Steward user needs a browser session, and there is no non-browser path
  ([apelogic-ai/steward#179](https://github.com/apelogic-ai/steward/issues/179)).
- **No real Google login in CI.** The browser-admin test proves everything up
  to the redirect to Google; the sign-in, the session and every administrator
  action are covered only by the manual
  [first-admin runbook](../browser-admin/first-admin.md) and
  [walkthrough](../browser-admin/walkthrough.md).
- **amd64 only.** Steward images are linux/amd64 only
  ([apelogic-ai/steward#148](https://github.com/apelogic-ai/steward/issues/148)).
- **Google Workspace and GitHub.com are required** for browser login and
  governed use. Personal Google accounts, GitHub Enterprise Server and GitLab
  are not supported. See [prerequisites](../prerequisites.md).
- **mcp-gw is pinned but not exercised.** Nothing installs it until the
  governed profile exists.
- **Kubernetes 1.35 and 1.36 are not in the window.** The pinned
  github-oidc-exchange 0.7.2 allows only TCP 443 egress, which blocks its
  replay ledger where the API server is reached on another port after
  address translation, as on the kind v0.33.0 node images for 1.35 and 1.36
  ([apelogic-ai/github-oidc-exchange#58](https://github.com/apelogic-ai/github-oidc-exchange/issues/58),
  fixed in a later exchange release that this BOM does not pin yet).
- **Built mode is not installed in CI.** Its generation and its refusals are
  tested; no end-to-end test installs built products, and nothing yet checks
  that running workloads use the lock digests
  ([#37](https://github.com/apelogic-ai/steward-platform/issues/37)).
- **Source-built mode needs the BOM's product releases.** The lock's product
  versions, commits and chart versions must equal the BOM's, so newer product
  releases cannot be built into this BOM
  ([#34](https://github.com/apelogic-ai/steward-platform/issues/34)).
- **The Flux output covers the production shape only.** Environments that use
  evaluation pieces (evaluation CA, PostgreSQL, edge CA or Gateway) get no
  Flux output, and the Flux reconcile job reconciles only the task-auth edge.
- **No automated BOM bumps or signed platform releases yet**
  ([#4](https://github.com/apelogic-ai/steward-platform/issues/4)).

## Known issues

- **Flux in built mode from a private registry needs a Kustomize patch.** The
  generated product `OCIRepository` objects carry no `secretRef`, because the
  platform values' Flux credentials belong to `registry.productCharts`, which
  built mode refuses. Give Flux's source controller access to your registry
  yourself, for example with a Kustomize patch that adds `spec.secretRef` or
  `spec.provider` to those objects. See
  [fork and build from source](../fork-and-build.md#4-generate-in-built-mode).
- **The evaluation PostgreSQL chart takes no image pull Secret.** For an
  evaluation install from an authenticated mirror, give the nodes credentials
  for the mirror. See [registry mirroring](../registry-mirroring.md#limits).
- **Changing profile in place** leaves the disabled releases installed, and
  task-auth to browser-admin fails on a `BackendTLSPolicy` ownership clash
  ([#33](https://github.com/apelogic-ai/steward-platform/issues/33)).
- **CI flake**: Steward can install before the evaluation CA is ready, so a
  browser-admin end-to-end run occasionally times out; a rerun passes
  ([#29](https://github.com/apelogic-ai/steward-platform/issues/29)).
- The product issues listed in the
  [alpha.5 notes](2026.10.0-alpha.5.md#known-product-issues) still apply: the
  products are the same releases.
