# Steward platform 2026.10.0-alpha.10

A pre-release of the Steward platform BOM that moves two products to their
current releases: Steward 0.3.8, which adds browser Run now, member
administration and automatic GitHub identity association and fixes a critical
Next.js advisory, and mcp-gw 0.5.7, still pinned for the planned governed
profile. github-oidc-exchange 0.7.5 and steward-run 0.7.6 are unchanged. The
platform itself (generator, helmfile, Flux output, scripts, platform values
schema) is unchanged from [2026.10.0-alpha.9](2026.10.0-alpha.9.md). It is an
alpha: the governed profile, which runs agents, is not in it yet.

**No breaking changes for the core, task-auth and browser-admin profiles.**
Platform values written for alpha.9 validate unchanged and generate the same
install with the new product coordinates. Steward 0.3.8 adds additive database
migrations 0052 to 0063, so rolling back to 0.3.5 needs a database restore
([Steward 0.3.8](#steward-038)). Its new governed-only chart values
(`spire.className`, `spire.sandboxRegistration`) do not apply to these
profiles, which do not enable execution.

[`bom/bom.json`](../../bom/bom.json) at this version is authoritative. The
tables below abbreviate digests to 12 hex characters for reading; install from
the full digests in the BOM, never from tags.

### What changed in each product

#### Steward 0.3.8

[Release notes](https://github.com/apelogic-ai/steward/releases/tag/v0.3.8),
[changelog](https://github.com/apelogic-ai/steward/blob/v0.3.8/CHANGELOG.md).
0.3.6 and 0.3.7 were published incompletely and must not be used: 0.3.6
stopped at the release vulnerability gate, and 0.3.7's clean-cluster
acceptance failed before its release handoff. 0.3.8 contains every 0.3.6 and
0.3.7 change. From 0.3.5, the changes are:

- **Security: Next.js 16.3.6.** The web application is updated from Next.js
  16.3.3 to remediate the critical advisory `GHSA-vcvr-r3jv-pc5j`.
- **Browser Run now** for inline task packages, exact Git package locators and
  published Workflows, with the signed-in user's selected User Envelope,
  bounded JSON inputs, four active browser Tasks per user, owner-scoped `out/`
  downloads, and a live Run page over one held server-sent event stream.
- **Member administration in the browser**: invite organization email
  addresses before first sign-in, assign roles and administrator access, link,
  unlink or disable federated identities, and disable and re-enable members.
  This gives the [walkthrough](../browser-admin/walkthrough.md)'s identity
  association step a page; the browser API it documents still works.
- **Automatic GitHub identity association.** With
  `taskIdentity.federatedSubjects.autoAssociateFromConnections` (default
  `true`), a `steward-task-v3` subject is associated when the same user
  verifies the same numeric GitHub account through GitHub Connect. This needs
  the governed Connections lane and mcp-gw connection-status v2 (0.5.5 or
  later), so it does not change the profiles in this BOM, where association
  stays manual.
- **Clearer task-auth answers.** A verified `steward-task-v2` credential
  that names an unknown canonical user now gets
  `403 task_identity_unknown_user` instead of `401`. An unassociated
  `steward-task-v3` subject still gets `403 task_identity_unassociated`.
- **Administrator Get started workspace** with live, read-only setup checks,
  and an explicit remote or vendored installation mode for generated
  steward-run callers (`config.apiserver.stewardRunWorkflowInstallationMode`,
  default `remote`).
- **Additive migrations 0052 to 0063** (connection-operation diagnostics,
  connection-verified federated subjects, Task source provenance with a
  guarded backfill, browser Tasks and members). The apiserver and controller
  apply them on startup, and they change no existing row's meaning.
- **Governed only: SPIRE class and sandbox registration.** The chart now
  requires `spire.className` when execution is enabled and, by default,
  creates the OpenShell sandbox `ClusterSPIFFEID`
  (`spire.sandboxRegistration.enabled`). Governed installs outside this BOM
  must choose exactly one owner for that registration before upgrading; see
  [upgrading](#upgrading-from-2026100-alpha9).

The generated Steward values change only in image tags and digests; the new
chart values keep their defaults. The provider-profile bundle stays at
`steward-runtime-providers@1.2.2`.

#### github-oidc-exchange 0.7.5 and steward-run 0.7.6

Unchanged from alpha.9; see
[the alpha.8 notes](2026.10.0-alpha.8.md#github-oidc-exchange-075). Steward's

#### mcp-gw 0.5.7

[Release](https://github.com/apelogic-ai/mcp-gw/releases/tag/v0.5.7),
[changelog](https://github.com/apelogic-ai/mcp-gw/blob/v0.5.7/CHANGELOG.md).
0.5.5 published images but no chart or release; 0.5.6 contains all its
changes. From 0.5.4, the changes are:

- **Stable GitHub account identity.** Connection-status contract version 2
  (opt-in through the `Accept` header) exposes the connected account's
  immutable numeric ID; version 1 stays the byte-compatible default. Existing
  connections are backfilled on their first status read, without a reconnect.
  Forward-only migration `008_provider_account_identity.sql` runs through the
  chart's migration path.
- **Stable lifecycle error codes** on connection failures, and one sanitized
  wrapper warning for every OAuth or lifecycle `4xx`/`5xx`.
- **An attested GitHub governance catalog** release asset
  (`github-governance-catalog.json`) listing every pinned GitHub MCP Server
  tool, grant tuple, access class and toolset. The BOM does not pin it.

No OAuth reconnect, Secret format change, chart value rename or new required
value. No profile installs mcp-gw.

## Upgrading from 2026.10.0-alpha.9

- **Platform values** from alpha.9 validate against the current schema
  unchanged and, with this BOM, generate exactly what alpha.9's generator
  generates. Regenerating changes only product coordinates: the Steward chart
  digest, the Steward image tags and digests, the `platformVersion` in the
  header comments and, in the task-auth and mirrored Flux output, the
  `steward-platform` `GitRepository` tag, to `2026.10.0-alpha.10`.
  github-oidc-exchange, `stewardRunRelease` and `charts/steward-edge` are
  unchanged.
- **Back up the Steward database first.** The apiserver and controller apply
  migrations 0052 to 0063 on startup. They are additive, but rolling back to
  0.3.5 means restoring that backup together with the 0.3.5 chart and image
  set.
- **Apply** with `helmfile --environment <env> --kube-context <context>
  sync`, or let Flux reconcile the regenerated objects. Deploy the Steward
  chart and images as one release unit.
- **Browser sessions** live in the apiserver process, so the rollout signs
  everyone out once.
- **Steward governed users** (outside this BOM): before upgrading, set
  `spire.className` to the class your SPIRE controller manager watches, in both
  the platform-preflight input and the chart values. Then pick one owner for
  the OpenShell sandbox `ClusterSPIFFEID`: remove a platform-owned one before
  keeping the chart default, or set `spire.sandboxRegistration.enabled=false`
  and keep yours, with the selectors and SPIFFE ID template that Steward's
  [OpenShell guide](https://github.com/apelogic-ai/steward/blob/v0.3.8/docs/installation/openshell-v0.0.98.md)
  documents. Rerun the 0.3.8 platform preflight with that choice. No
  provider-profile transition is needed.
- **mcp-gw** is not installed by any profile. If you installed the pinned
  0.5.4 yourself, the 0.5.5 migration runs through the chart's migration path,
  and a browser that passes `redirectAfter` must have its exact origin in
  `githubWrapper.oauth.redirectAfterAllowedOrigins`.
- **Registry mirror.** Copy the new Steward and mcp-gw artifacts before
  regenerating: `scripts/mirror-list.sh` lists them, and
  `scripts/verify-digests.sh --mirror <platform-values>` checks the copy.
- **Built from source.** Rebuild Steward at the new release commit and write
  a new lock: the lock's versions, chart versions and commits must equal this
  BOM's, so an alpha.9 lock is refused.
- **Coming from a pre-platform install**: follow the
  [migration runbook](../upgrades/from-pre-platform.md), which lists the
  upgrade notes to apply in order.
- **Rolling back** to alpha.9 means generating from an alpha.9 checkout and
  restoring the pre-upgrade Steward database with the 0.3.5 release unit.

## What it proves

CI runs every check on each pull request, on each push to `main` and nightly,
on GitHub-hosted amd64 runners. With the new product releases, everything
alpha.9 proved still holds: the core, task-auth and browser-admin end-to-end
tests run on every Kubernetes version in `kubernetes.tested`, install through
the reference install, and take every coordinate from the BOM. They install
Steward 0.3.8, run its new migrations on a fresh database, and the task-auth
test runs the steward-run 0.7.6 action against Steward 0.3.8 and
github-oidc-exchange 0.7.5 with a real GitHub Actions OIDC token and asserts
the same `403 task_identity_unassociated` answer. See
[the alpha.5 notes](2026.10.0-alpha.5.md#what-it-proves) for what each test
asserts, and [the alpha.6 notes](2026.10.0-alpha.6.md#what-it-proves) for the
registry mirror, built mode, CRD hook, Flux and backward compatibility checks.

The other checks: every pinned digest resolves anonymously; Steward's and
mcp-gw's GitHub artifact attestations verify against the release workflow at
the release tag and the pinned commit; github-oidc-exchange's and
steward-run's cosign bundles verify, and their signed release manifests name
every pinned digest. See [verification](../verification.md).
