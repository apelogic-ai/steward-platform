# Steward platform 2026.10.0-alpha.5

The first tagged pre-release of the Steward platform BOM. It is a set of
product releases and dependency versions that CI installs and tests together,
pinned by digest. It is an alpha: the governed profile, which runs agents, is
not in it yet.

[`bom/bom.json`](../../bom/bom.json) at this version is authoritative. The
tables below abbreviate digests to 12 hex characters for reading; install from
the full digests in the BOM, never from tags.

### Kubernetes

## What it proves

CI runs every check on each pull request, on each push to `main` and nightly,
on GitHub-hosted amd64 runners. The three end-to-end tests run on every
Kubernetes version in `kubernetes.tested` (1.32 to 1.34), install through the reference
install (the generator and helmfile), and take every coordinate from the BOM.

- **core** ([test](../../tests/e2e/core/README.md)): Steward installs from its
  BOM chart digest and runs its BOM image digests next to cert-manager and
  evaluation PostgreSQL; every database migration applies; cert-manager issues
  both Steward certificates and injects the webhook CA; the admission webhook
  (`failurePolicy: Fail`) denies an invalid `AgentRuntime`; the API answers
  `401` on an admin route over verified TLS.
- **task-auth** ([profile](../profiles/task-auth.md),
  [test](../../tests/e2e/task-auth/README.md)): with a real GitHub Actions
  OIDC token from the CI job, the profile installs behind an Envoy Gateway
  edge with verified TLS at both hops; discovery through the edge agrees
  between Steward and github-oidc-exchange, and Steward holds the exchange's
  published keys; the released steward-run action at the BOM action commit
  exchanges a fresh GitHub token and submits, and Steward authenticates it
  and refuses it with `403 task_identity_unassociated`, creating no Task;
  driven directly, the exchange returns a 120-second `steward-task-v3` token
  for the job's actor, Steward answers it `403 task_identity_unassociated`
  naming the exact issuer and subject, and answers `401` to an invalid token
  and to the raw GitHub token; the exchange rejects a replayed assertion, a wrong
  audience and a workflow its policy does not admit, each with its audit
  event.
- **browser-admin** ([profile](../profiles/browser-admin.md),
  [test](../../tests/e2e/browser-admin/README.md)): the profile installs with
  a placeholder Google OAuth client; the web UI, apiserver, controller,
  exchange and edge run their BOM digests and the web UI is ready through the
  edge; the apiserver carries the configured browser login and steward-run's
  release coordinates, which equal steward-run's signed release manifest
  under Steward's mapping; Steward's own routes carry every public API path
  to the apiserver and the rest to the web UI; `GET /admin/auth/login`
  redirects to `accounts.google.com` with the configured client ID, the exact
  redirect URI, the hosted domain and PKCE.

The other checks: the BOM validates against its schema and cross-references;
every pinned digest resolves anonymously; Steward's and mcp-gw's GitHub
artifact attestations verify against the release workflow at the release tag
and the pinned commit; github-oidc-exchange's and steward-run's cosign
bundles verify, and their signed release manifests name every pinned digest
(and, for steward-run, exactly the action and workflow coordinates Steward
is configured with); the generator and helmfile render every environment
against the pinned charts; the Flux example matches a fresh generation. See
[verification](../verification.md).

## How to verify it yourself

From a checkout of this repository at the release tag, with the tools listed
in [verification](../verification.md):

```sh
scripts/validate-bom.sh
scripts/verify-digests.sh
GH_TOKEN=... scripts/verify-attestations.sh
scripts/verify-signatures.sh
tests/generate/run.sh
FLUX_SCHEMAS_DIR=... tests/flux/run.sh
```

`verify-attestations.sh` needs a GitHub token, because `gh attestation
verify` reads attestations through the GitHub API; the others need no
credentials. The end-to-end tests need an amd64 Docker host; the task-auth
test also needs a GitHub Actions job that can request an OIDC token.

## What it does not do yet

- **No governed Task execution.** There is no governed profile: no runner
  scale set, Mint, SPIRE, sandbox or inference proxy is installed or tested
  ([#3](https://github.com/apelogic-ai/steward-platform/issues/3)).
- **No Task is admitted.** The task-auth test stops at
  `403 task_identity_unassociated`: associating a federated subject with a
  Steward user needs a browser session, and there is no non-browser path
  ([apelogic-ai/steward#179](https://github.com/apelogic-ai/steward/issues/179)).
- **No real Google login in CI.** The browser-admin test proves everything up
  to the redirect to Google; the sign-in, the session and every administrator
  action are covered only by the manual
  [first-admin runbook](../browser-admin/first-admin.md) and
  [walkthrough](../browser-admin/walkthrough.md).
- **The browser-admin walkthrough has not yet been run end to end by a
  person** against this BOM.
- **amd64 only.** Steward images are linux/amd64 only
  ([apelogic-ai/steward#148](https://github.com/apelogic-ai/steward/issues/148)).
- **Google Workspace and GitHub.com are required** for browser login and
  governed use. Personal Google accounts, GitHub Enterprise Server and GitLab
  are not supported. See [prerequisites](../prerequisites.md).
- **mcp-gw is pinned but not exercised.** Nothing installs it until the
  governed profile exists.
- **Kubernetes 1.35 and 1.36 are not in the window.** On the kind v0.33.0
  node images for 1.35 and 1.36 the CNI evaluates NetworkPolicy after the API server
  Service address is translated to its endpoint port, and
  github-oidc-exchange's egress policy (TCP 443 only) then blocks its replay
  ledger, so every exchange fails; core and browser-admin pass there, but
  task-auth does not
  ([apelogic-ai/github-oidc-exchange#58](https://github.com/apelogic-ai/github-oidc-exchange/issues/58)).
  The same applies on any CNI that behaves this way.
- **Flux output covers the core profile only.**
- **No automated BOM bumps or signed platform releases yet**
  ([#4](https://github.com/apelogic-ai/steward-platform/issues/4)).

## Known product issues

- Steward: [#148](https://github.com/apelogic-ai/steward/issues/148)
  multi-arch images and scheduling values;
  [#152](https://github.com/apelogic-ai/steward/issues/152) NetworkPolicy
  takes literal CIDRs only, including for Google sign-in egress;
  [#146](https://github.com/apelogic-ai/steward/issues/146) no documented
  operator CLI credential;
  [#179](https://github.com/apelogic-ai/steward/issues/179) no non-browser
  path to associate a Task identity;
  [#180](https://github.com/apelogic-ai/steward/issues/180) no API-only edge
  without the web UI and browser login;
  [#150](https://github.com/apelogic-ai/steward/issues/150) preflight has no
  core profile.
- github-oidc-exchange:
  [#55](https://github.com/apelogic-ai/github-oidc-exchange/issues/55)
  `keyring-tool` is not shipped as a release binary;
  [#56](https://github.com/apelogic-ai/github-oidc-exchange/issues/56)
  NetworkPolicy ingress guidance;
  [#58](https://github.com/apelogic-ai/github-oidc-exchange/issues/58)
  egress allows only TCP 443, so the replay ledger fails where the API
  server is reached on another port after address translation.
- steward-run: [#69](https://github.com/apelogic-ai/steward-run/issues/69)
  the action needs Node 24 on `PATH` without declaring it;
  [#70](https://github.com/apelogic-ai/steward-run/issues/70) network egress
  and proxy support.
- mcp-gw: [#80](https://github.com/apelogic-ai/mcp-gw/issues/80) Google Cloud
  setup is undocumented.

## Changes since 2026.10.0-alpha.4

- Steward 0.3.1 to 0.3.2. The chart now requires Kubernetes 1.32, requires
  exactly Steward's seven public API paths and `[PathPrefix /]` as its
  `web.httpRoute` path lists (the generator already produced exactly these),
  and requires at least one character after `org_` in
  `browserAuth.google.organizationId`; the platform values schema follows.
- github-oidc-exchange 0.7.1 to 0.7.2.
- steward-run 0.7.1 to 0.7.2, with its new action commit and workflow commit.
- mcp-gw 0.5.0 added, pinned for the planned governed profile. The BOM schema
  gains `products.<name>.plannedFor` for a product that no implemented
  profile uses yet.
